## 1. Headline — are we okay?

**Yes.** Every finding from the June review re-verifies: nothing regressed, the three
fixes applied then (anonymous email leak, `/api/slides` rate limiting, comment
author-email spoofing) all still hold, and — the thing this review was really for —
the **new surfaces built since June (floating viewer, feed, spectrum, the three
per-viewer hooks) correctly inherited the security model**. The email redaction for
anonymous viewers was extended to the feed and spectrum paths; the iframe sandbox is
`allow-scripts`-only everywhere (`allow-same-origin` appears **nowhere**, confirmed by
exhaustive search); all write paths still resolve the user server-side from the
session, never from the client. No critical or high findings.

What's new is a handful of **medium** items: one real gap in the Chrome extension
(its iframe capture handler will answer *any* website that asks, not just Claude —
a cheap fix), one infrastructure-dependent OAuth caution (the server trusts forwarded
headers to learn its own address), and — on the quality side — the discovery that the
**default (floating) viewer and the feed silently swallow load errors** that the
classic viewer would have surfaced, and that **feedback left in the classic viewer is
invisible to your G1 analytics**. Details below.

## 3. New security findings

### NS1 — Extension: iframe capture handler answers *any* origin — **Medium**

**What it is:** the extension's content script runs inside Claude's artifact iframes
(`*.claudeusercontent.com` etc.) and listens for a "capture" message. The listener
checks only the message's shape — `data.__slidehuddle === "capture"` — **never
`event.origin`** — and replies with the frame's full HTML to whoever asked, addressed
to `"*"` ([content.js:108-134](../content.js)).

**Why it matters:** if any third-party website can embed one of those artifact URLs in
an iframe, it could send that message and — for a user with the extension installed —
receive the artifact's HTML, which a cross-origin page normally cannot read. The
extension would be *adding* an exfiltration path to the browser. Exploitability
depends on whether Anthropic's servers allow those pages to be framed by other sites
(their `frame-ancestors` policy — not visible from this repo, so **uncertain**). This
is the June L3 finding, upgraded now that the write-up traced the actual reply path.

**Recommended fix:** in both message listeners (`installIframeHandler` and the
top-frame `capture-result` listener), check `event.origin` against the known Claude
origins and reply with a specific `targetOrigin` instead of `"*"`. Cheap, and closes
the question regardless of Anthropic's framing policy.

### NS2 — OAuth/MCP: the server learns its own address from forwardable headers — **Medium (uncertain)**

**What it is:** the OAuth discovery metadata, token issuer, and every `share_url` are
built from a "public origin" derived from `x-forwarded-host` / `forwarded` request
headers (via the mcp-handler dependency; used in
[oauth/authorize/route.ts](../web/src/app/oauth/authorize/route.ts),
[mcp/route.ts](../web/src/app/mcp/route.ts), and both `.well-known` routes). Nothing
pins it to `slidehuddleapp.vercel.app`.

**Why it matters:** on Vercel these headers come from the trusted proxy, so in normal
production this is safe — tokens can't be forged either way (the signing secret is a
static env var). But if any path lets a request reach the function with a spoofed
header (misconfigured proxy, preview deployments), discovery metadata and share links
would point at an attacker's host. **Recommended fix:** set an explicit canonical-origin
env var and use it instead of trusting forwarded headers. Flagged medium because
exploitability depends on infrastructure guarantees we can't see from the code.

### NS3 — No length cap on owner-curation text — **Low**

**What it is:** the original user-text columns all have database length limits
(comments ≤4000, stub title ≤200, flag reason ≤2000 — the June review was right). But
the newer curation columns `owner_edited_body` / `owner_edited_reason`
([feedback-curation-migration.sql](feedback-curation-migration.sql)) have **no** length
check, and they're written through the service-role client (bypassing RLS) by the
curation server actions, which whitelist *which* fields may change but don't validate
their size ([slide-store.ts](../web/src/lib/slide-store.ts) `setCommentCuration` etc.).
A deck owner could store megabytes of text per comment.

**Why it matters:** owner-only, so it's self-inflicted storage/prompt bloat rather
than an attack on others — but it's the one write path with no size guard at any
layer. **Recommended fix:** cap the patch fields in the server actions (mirror the
original columns' limits) and/or add matching `CHECK` constraints in a small migration.

### NS4 — `/api/deck-version` is unauthenticated and unthrottled — **Low**

**What it is:** the new polling endpoint ([api/deck-version/route.ts](../web/src/app/api/deck-version/route.ts))
returns a deck's latest version number to anyone, with no rate limit. Deliberate and
documented ("nothing sensitive, deck is public-by-link"), and deck ids are unguessable
(~122 bits), so exposure is minimal — but it's a free database read per request and a
deck-existence oracle. **Recommended fix:** add the existing per-IP limiter (one import
+ one check, same as `/api/slides`).

### NS5 — `/api/recount-my-decks` backfill utility live in production — **Low**

**What it is:** a one-shot maintenance endpoint ([api/recount-my-decks/route.ts](../web/src/app/api/recount-my-decks/route.ts))
that re-derives title/slide-count for every deck you own. Properly authed and scoped to
the caller's own decks, so no cross-user risk — but each call loads the **full HTML of
every owned deck** and it has no rate limit, so a signed-in user can self-inflict heavy
load. It's also served its purpose. **Recommended fix:** remove it, or keep it behind
an env flag.

### NS6 — OAuth authorization codes are not single-use — **Low**

Codes are only bounded by their 60-second TTL; there's no used-code list
([mcp-oauth.ts:50-53](../web/src/lib/mcp-oauth.ts) — an explicit, documented v1
trade-off). PKCE means a leaked code alone isn't enough, so residual risk is low.
Feed this into the dedicated OAuth review (below); the standard hardening is a
used-code nonce/table.

### NS7 — Realtime updates re-expose the *stored* comment author email — **Info / uncertain**

The M4 fix re-resolves the displayed author email from the trusted `user_id` at read
time. But the hooks' realtime UPDATE handlers merge the raw database row into state
(`{ ...c, ...row }` in [useDeckComments.ts:84-86](../web/src/app/viewer/useDeckComments.ts)),
which overwrites the server-resolved email with the stored snapshot. If the M4 insert
policy is applied in prod, the stored value can't be spoofed anymore and this is moot —
which is why confirming that migration (headline caveat) matters. Including it because
I'm uncertain rather than staying silent; a one-line fix is to drop `author_email`
from the merged fields.

### What was checked and came back clean (so silence is meaningful)

The new-surface sweep specifically looked for a repeat of the June email-leak class of
bug and found none: feed and spectrum reuse the same redaction helpers; anonymous
viewers get zero comments, zero participant identities, and a count-only chip; the
hooks' writes go through RLS (browser client) or session-authenticated server actions
identically to the classic paths. OAuth's core shape is solid: PKCE required (S256
only, constant-time compare), redirect URIs exact-matched against the registered
client *before* any redirect, `/mcp` requires a valid token on every call with all
inputs zod-validated and size-capped, and per-user rate limiting is in place. The
extension still requests only the `storage` permission, stores the write token in
`chrome.storage.local` (unreadable by web pages), never auto-sends in Claude, and the
feedback autofill is text-only, empty-composer-only, with the fragment stripped so a
refresh can't re-fill.

## 4. Code-quality findings

### Q1 — Load errors never reach the default viewer or the feed — **Medium**

The whole point of the `{ rows, failed }` pattern is "never show a false empty state" —
and the classic viewer honours it. But [page.tsx](../web/src/app/viewer/page.tsx)
passes `loadErrors`/`deckLoadFailed` **only to `SlideViewer`** (lines 623-624).
`FloatingViewer` — the default for everyone — and `DeckFeed`/`FeedStream` have no such
props: the feed branch reads `.rows` and discards `.failed` entirely (page.tsx:404-411).
A failed comments/stubs/flags query renders as "no data" / "No conversation yet" for
nearly all users; only `?view=classic` says "Couldn't load — try refreshing."
**Fix:** add the props and a small error banner to FloatingViewer and the feed.

### Q2 — Classic-viewer feedback is invisible to G1 analytics — **Medium**

The three hooks fire `track("feedback_added", …)` on confirmed saves; the classic
viewer's equivalent handlers ([SlideViewer.tsx:461-676](../web/src/app/viewer/SlideViewer.tsx))
fire nothing. Anyone using `?view=classic` produces feedback your Gate-G1 numbers never
see. **Fix:** since SlideViewer is frozen, either accept and *document* classic as
analytics-blind in `docs/G1-MEASUREMENT.md`, or make this the one sanctioned exception
to the freeze.

### Q3 — `getOwnerEmails` is an N+1 on the render path — **Medium (performance)**

One `auth.admin.getUserById` HTTP call **per unique user id**, and it runs inside up to
six loaders per stored-deck view (stubs, flags, comments, participants — plus the feed's
all-version comments and second stub/flag loads), re-resolving the same people
repeatedly ([slide-store.ts:1602-1626](../web/src/lib/slide-store.ts)). Fine at today's
scale; will visibly slow busy decks. **Fix:** batch via `listUsers` or a per-request
memo passed through the loaders.

### Q4 — Every feed card renders an eager iframe — **Medium (performance)**

[FeedItemCard.tsx:93-108](../web/src/app/viewer/FeedItemCard.tsx) gives every
comment/flag card a live `<iframe srcDoc>`. `LazyThumbnailStrip` was built precisely
because "a 6-version deck would otherwise spawn 30+ iframes" — but the per-card thumbs
never got the same treatment, so a 60-comment deck mounts 60 iframes plus the spine
strips plus the peek. **Fix:** reuse the LazyThumbnailStrip IntersectionObserver
pattern for card thumbnails.

### Q5 — Drift between the viewer copies (the known three-rendering duplication)

The deliberate duplication (classic frozen; floating + hooks; feed) is holding up
better than expected — the hooks are faithful extractions and the `FeedStream`
extraction from `DeckFeed` was clean (no stale second copy). The drift that *has*
crept in, each **Low**:

- **Dismissed-flag semantics differ.** Floating deliberately ignores dismissed flags
  (`!f.dismissed`, [FloatingViewer.tsx:734-742](../web/src/app/viewer/FloatingViewer.tsx));
  classic counts them, so a dismissed flag still marks the slide flagged and blocks
  re-flagging there ([SlideViewer.tsx:418-424](../web/src/app/viewer/SlideViewer.tsx)).
- **Out-of-band revision behaviour + copy differ.** Classic silently `router.refresh()`es
  unless comments are open ("✨ This deck was just revised… " / "Show it"); floating
  always prompts ("This deck was revised — now on vN" / "Load vN"). Same 12s poll,
  copied, two outcomes.
- **Realtime-echo dedupe is inconsistent.** `useDeckFlags.addFlag` guards against the
  realtime echo duplicating the row; `useDeckStubs.insertStub` and both classic insert
  handlers don't — a fast echo shows the item twice.
- **Floating thumbnail rail has no flagged-slide indicator** (classic's dim + trash
  icon); already noted in BEHAVIOURS.md D1 but worth a decision.
- **Deck parsed up to three times.** `DeckFeed` and `FeedStream` each run
  `parseDeck(rawHtml)` and build full srcdoc arrays (DeckFeed uses only one); spectrum
  adds a third parse in FloatingViewer. Lift the parse to the host.
- **Feed/spectrum double-fetches stubs and flags** — once open-only for the viewer,
  again with `includeResolved` for the feed (page.tsx:179-186 vs 403-411). Fetch once
  with `includeResolved` and filter. (Redaction itself is shared — one copy — good.)

### Q6 — `{ rows, failed }` violations inside the data layer — **Low**

- `getDeckVersionHtml` returns `null` for both "not found" and "query errored" — a DB
  error while loading a historical version silently falls back to the current version.
- `getDeckView` returns `null` on error → reads as "first-time viewer", silently
  suppressing the arrival/updated banners.
- `getDeckShareCounts` and `getOwnerEmails` swallow errors as `{}` / skip — a transient
  auth-API failure shows "Someone" as every author with no signal.

### Q7 — Arrow keys navigate slides while typing a comment — **Low (bug, both viewers)**

Both viewers' global ArrowLeft/Right handlers lack the INPUT/TEXTAREA guard that the
floating viewer's `T` shortcut already has ([FloatingViewer.tsx:379-387](../web/src/app/viewer/FloatingViewer.tsx)
vs :504-513; same in SlideViewer). Moving the caret in the composer changes the slide
under your half-written comment. A fix must land in both copies (or classic accepted
as-is per the freeze).

### Q8 — Dead / leftover code — **Low / Info**

- `.wip-backup/` at the repo root holds stale copies of `FloatingViewer.tsx` and
  `HuddleAvatars.tsx`; `docs/design-decision-feed-model (1).md` is a "(1)"
  duplicate-download name. Delete or gitignore.
- `CommentsPanel`'s `isStub` branches are unreachable — both viewers always pass
  effectively `false`. Remove or mark reserved.
- `shared_decks.role` is written as `'viewer'` always and read never (June L2).
- `FLOATING_VIEWER_DEFAULT` / `FEED_PARTNER_EMAILS` / all five `?view=` values are
  live, documented escape hatches — fine, but list them for retirement at the Phase-7
  cutover.
- Extension popup shows `v0.1.0` while the manifest says `0.4.0` (cosmetic).

### Q9 — Type safety — **Info**

Genuinely clean: **no `: any` or `as any` in web/src**, both `JSON.parse` sites are
guarded, MCP inputs are zod-validated. Two notes: realtime payloads are cast
(`payload.new as CommentRow`) and merged into state without a field check — a cheap
presence-guard would harden it; and the `as unknown as` casts in slide-store are all
documented workarounds for generated Supabase types lagging the migrations —
regenerate the types and delete them.

### Q10 — Known consistency splits, confirmed still present — **Info**

- Copy (BEHAVIOURS.md I3): "Send to AI" (floating) vs "Send to Claude" (classic);
  "Won't action" (feed) vs "Won't send to Claude" (panel/stubs). Plus the new revision
  banner split (Q5). Unification is already a decided founder choice, scheduled for
  spectrum Slice 2/3 — just don't lose the list.
- Avatars (BEHAVIOURS.md I1): `Avatar.tsx` centralisation holds, but `CommentsPanel`
  still uses its own flat purple-circle avatar and `AvatarMenu` keeps a plain-chip
  fallback in TopNav.
